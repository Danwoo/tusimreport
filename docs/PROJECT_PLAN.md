# TuSimReport 개발·완성 계획

일반 작업 계획 문서다. 기존 CLAUDE.md를 대체하지 않으며, 구현·실행·배포 결과는 실제로 확인한 범위만 기록한다.

## 목표와 범위

한국 주식 한 종목을 입력하면 실제 데이터를 수집하고, 근거와 기준 시점이 표시된 분석 리포트를 생성한 뒤 후속 질문에 답하는 흐름을 완성한다. 첫 버전은 기존 설계에 맞춰 개인이 사용하는 단일 사용자 연구 도구로 유지한다.

주문 실행, 실시간 호가, 다중 사용자 SaaS는 이번 범위에 넣지 않는다. 리포트 품질은 데이터 정확성·근거 일치·불확실성 표시로 검증한다. LLM의 신뢰도 점수를 수익 확률이나 검증된 예측 성능으로 설명하지 않는다.

## 현재 확인한 상태

2026-10-02 main의 문서와 선택한 코드를 읽었다. 전체 코드를 실행하거나 외부 API·배포를 검증한 것은 아니다.

- Streamlit UI, LangGraph 기반 분석, 후속 대화, 외부 데이터 클라이언트가 있다.
- core/progressive_supervisor.py에는 독립 전문가 7개 병렬 실행과 재무·상대평가 2개 순차 실행이 있다. 최종 보고서 경로는 9개 실행 성공 여부를 확인한다.
- docker-compose.yml에는 Chromium 실행을 고려한 설정, 캐시 볼륨, healthcheck가 있다. 실제 컨테이너 실행은 별도 확인이 필요하다.
- .github/workflows/ci.yml은 Python 3.11/3.12, ruff, 일부 모듈 mypy, pytest 커버리지 하한 45%, 시크릿 검사를 구성한다. 의존성 감사는 실패를 차단하지 않는 설정이다. 최신 실행 결과는 따로 확인한다.
- 실제 서비스 운영은 미완료다. 코드·CI 구성의 존재와 운영 성과를 구분한다.

## 먼저 정리할 문서와 동작 차이

| 항목 | 확인한 차이 | 다음 작업 |
|---|---|---|
| Docker | README에 실행 방법과 미지원 설명이 함께 있음 | 실제 빌드·실행을 확인한 뒤 설명 통일 |
| 분석 수 | 현재 구조는 9명인데 후속 대화 설명에는 8명이라고 적힘 | 실제 전달되는 컨텍스트 확인 후 수정 |
| 필수 API | README는 최소 키 3개, config/settings.py는 LLM 필수·DART/ECOS 제한 경고 | 부분 분석과 충분한 분석의 조건을 분리 |
| 테스트·감사 | 문서 수치와 CI 설정이 다르고 감사 실패는 차단되지 않음 | 최신 결과와 실제 차단 조건을 구분 |
| 부분 실패 | 보고서 생성과 투자 의견 생성의 통과 조건을 동일하다고 볼 수 없음 | main.py와 합성 경로까지 추적해 정책 명시 |

현재 설명의 차이를 곧바로 런타임 버그로 단정하지 않는다. 재현한 뒤 수정한다.

## 단계별 작업

### 1. 실제 데이터 연결부터 확인

- 브랜치·변경 사항·저장소 지침을 읽고 기존 작업을 보존한다. 실행 환경은 기존 CI의 Python 3.11/3.12와 의존성 파일을 기준으로 확인한다.
- 대표 종목 하나로 시세, DART 재무·공시, 거시지표, 뉴스 등 소스별 연결 상태를 점검한다. 종목 코드, 거래일, 단위, 기간, 공시 정정 여부를 확인한다.
- 설정된 키가 있다는 검사와 실제 요청 성공을 구분한다. 키 누락, 401/403, 429, 시간 초과, 빈 결과, 휴장일을 각각 확인한다.
- 운영 분석에는 실제 데이터를 사용한다. 자동 테스트의 HTTP 모의 응답은 허용하되 실제 연동 증거와 혼동하지 않는다. 누락된 값은 추정해 채우지 않는다.

완료 기준: 소스별 성공·실패, 데이터 기준 시점, 사용 가능한 분석 범위를 확인할 수 있다.

### 2. 근거를 확인할 수 있는 리포트 완성

- 각 분석에 데이터 출처와 링크 또는 문서 ID, 기준 시점, 관측값, 해석을 구분해 표시한다.
- 재무 수치와 비교 기준의 통화·단위·기간을 통일하고 수치 계산은 가능한 한 코드로 수행한다.
- 필수 근거가 부족하면 해당 분석을 제한하거나 보류한다. 에이전트 몇 개가 성공했다는 이유만으로 근거 없는 의견을 생성하지 않는다.
- 완료 신호 유무, 실행 성공, 데이터 충분성, 보고서 생성 가능성을 별도 상태로 다룬다.
- 후속 대화는 저장된 분석 근거와 범위 안에서 답하도록 확인한다. 기준 시점 이후의 질문에는 데이터 갱신 필요성을 표시한다.

완료 기준: 원천 자료로 주요 숫자와 주장을 대조할 수 있고, 누락·오래된 정보·분석 불일치를 화면에서 알 수 있다.

### 3. 반복 실행의 안정성과 비용 확인

- 여러 종목을 연속 분석할 때 전역 엔진·context manager·채팅 상태가 이전 결과를 잘못 전달하지 않는지 검사한다.
- 외부 요청과 에이전트 실행의 시간 제한, 재시도, 중단, 부분 실패 처리를 점검한다. 실패를 성공으로 보이게 하는 완료 신호 삽입은 하지 않는다.
- 병렬 실행 수를 API 호출 한도에 맞추고 캐시 TTL·갱신·재시작을 확인한다.
- 컨텍스트 예산 초과 시 실제 토큰 수가 줄어드는지 확인한다. 중요 근거가 빠지지 않도록 전달·요약 방식을 검증한다.
- 실행별 경과 시간, 요청 수, 토큰·비용, 소스/에이전트 성공 상태를 기록한다. 비용 단가는 확인 날짜와 함께 관리하고 비밀값은 로그에 남기지 않는다.

완료 기준: 반복 실행과 부분 실패를 재현할 수 있고 리포트 한 건의 비용·시간을 측정할 수 있다.

### 4. 리포트 품질과 구조의 효과 평가

- 대표 종목과 질문을 선정하고 고정된 기준 시점의 실제 데이터 스냅샷으로 평가한다.
- 숫자·단위·기간 정확성, 출처 추적 가능성, 근거 없는 주장, 데이터 부족의 적절한 표시를 평가한다. 자동 채점과 사람이 확인한 결과를 구분한다.
- 멀티에이전트와 단순 분석 기준선을 비교하려면 같은 입력 자료와 평가 질문을 사용하고 모델·토큰·시간·비용 차이를 기록한다.
- 테스트 건수·통과율·오류 유형·개선 전후 결과를 남긴다. 목표 수치와 실제 관측값을 분리한다.

완료 기준: 시스템을 복잡하게 만든 이득과 남은 오류를 결과로 설명할 수 있다.

### 5. 실행·배포·사용 검증

- 관련 테스트·린트·타입 검사와 Docker 빌드·healthcheck를 확인한다. CI 통과를 외부 API 통합 성공으로 표현하지 않는다.
- 우선 개인이 사용할 실행 환경을 정한다. 배포가 필요하면 비용·Chromium 의존성·캐시 보존·비밀 관리·로그·복구 방법을 비교한다. 유료 자원 생성과 외부 공개 범위는 사용자와 확인한다.
- 공개 시 누구나 유료 분석을 실행할 수 없도록 접근과 요청 한도를 정한다. 다중 사용자 서비스로 확장하는 일은 별도 계획으로 분리한다.
- 실제 사용 중 불편과 실패를 기록하고 작은 수정으로 개선한다. README를 확인된 실행 절차·지원 범위·남은 문제에 맞춰 정리한다.

완료 기준: 실제 데이터로 종목 입력 → 리포트 → 근거 확인 → 후속 대화 흐름을 사용하고, 장애 시 원인과 복구 방법을 확인할 수 있다.
